# 探针实测记录

这个文件记录那些「查文档查不出确定答案、只能实测」的结论。
每次跑完 `scripts/probe_deepseek_audio.py` 后把结果抄到这里，注明日期和模型名。

## 为什么需要探针

调研阶段关于「`deepseek-flash` 收不收音频输入」得到了**互相矛盾**的结论：

- 官方 Responses API 的内容块列表里只有 `input_text` / `input_image` / `reasoning_text`，
  **没有 `input_audio`**；第三方跨厂商对比（2026-08）也写明托管 API 不支持 audio。
- 但 2026 年 9 月确实存在过一个原生多模态内测版本，官方社区称可统一处理
  文本 / 图像 / 语音输入，模型 ID 为 `deepseek-v4.1-flash-expires-on-0910`
  —— 带过期后缀，已下线。
- 第三方网关（如 NagaAI）确实提供 `input_audio` 参数并能挂 `deepseek-v4.1-flash`，
  但文档注明模型读不了该 part 会返回 400 `unsupported_modality`。

结论既然有分歧，就不该靠猜来定架构。探针脚本用真实 API 跑一次，把这条钉死。

**注意**：无论探针结果如何，方案里「转写与复盘分两步」的架构都不变，因为还有两条更硬的约束：
90 分钟的录音远超单请求体积上限（必须切片），且大模型不做说话人分离
（而「区分面试官和我」正是本项目的核心需求）。

## 探针记录

### 2026-10-04 · `deepseek-flash` · 结论：**不支持音频**

运行命令：

```
backend/.venv/Scripts/python scripts/probe_deepseek_audio.py
```

| 探测项 | 结论 | 备注 |
|---|---|---|
| 模型列表 | 可用 | `deepseek-flash` 存在，账号下可见的模型只有它和 `deepseek-v4-pro` |
| JSON 输出模式 | 可用 | `response_format={"type":"json_object"}` 稳定返回可解析 JSON |
| 思考模式 + temperature | 不报错 | 服务端接受 `enable_thinking=true` 与 `temperature` 并存，不返回错误 |
| **音频输入** | **不支持** | 三种写法全部被拒 |

**关键证据** —— 服务端返回的错误信息直接列出了它接受的内容块类型：

```
HTTP 422 unknown variant `input_audio`, expected one of `text`, `image_url`, `file`
```

三种尝试（`input_audio`、`audio_url`、裸 `audio`）都是同一个 422，错误里那句
`expected one of text, image_url, file` 就是权威答案：**这台服务端的内容块只有
文本、图片、文件三种，没有音频**。注意 `file` 是文件类型（PDF 之类），不是音频。

这一条比调研阶段所有二手资料都可靠 —— 之前两个来源给的结论互相矛盾
（一方说支持音频，一方说纯文本），现在不用再猜了。

**对方案的影响**：无。架构本来就是「音频 → ASR → 文本 → DeepSeek」两步走，
理由也不只是这一条（90 分钟录音超单请求体积上限、大模型不做说话人分离）。
转录与复盘分离的设计无需调整。

**一个意外收获**：`enable_thinking=true` 与 `temperature` 同时传**不会报错**。
实现里可以少一层条件分支，不过按官方文档该参数在思考模式下会被忽略，
所以仍然不该指望用 `temperature` 控制思考模式的输出随机性。

## 2026-10-04 · 百炼 `paraformer-v2` 转写质量

端到端跑通用 `scripts/make_mock_interview.py` 合成的模拟面试音频（1 分 33 秒，
12 轮对话，中文语音合成）。这不是真人录音，所以**结论只对「技术名词识别」
和「接口链路」有效，「说话人分离」这次没测到**。

### 时延

提交到出结果约 **5 秒**（1.6 分钟音频）。这个速度很好，前端不需要等太久。

### 识别错误清单

| 原词 | 识别结果 | 性质 |
|---|---|---|
| `Raft` | `reft` | 英文专有名词拼错 |
| `key`（讲索引时说“重点看 key 这列”） | `接着` | **英文词被听成中文，语义完全错** |
| `隐式转换` | `引示转换` | 中文技术词 |
| `B+树` | `B加数` | 中文技术词 |
| `魏士杰`（人名） | `魏世杰` | 人名 |
| 句首的 `CAP` | 丢失 | 句首英文缩写被吞 |

**规律很清楚**：中文日常对话几乎全对，**中英混合的技术术语是薄弱点**。
`key → 接着` 这类错误尤其危险 —— 它在语义上完全说不通，但单看中文又很自然，
大模型后续分析时未必能察觉。

**可用的改进手段**：百炼支持自定义热词表，把面试常见的技术名词
（Raft、B+树、索引下推、隐式转换、CAP、MVCC…）加进去。
这是下一步值得做的事，成本几乎为零。

### 句级切分的一个真实风险

这次 `speaker_count=1`（合成音频只有一个音色，符合预期），于是暴露出一个
在真实场景也会发生的情况：

> 面试官问「如果线上发现数据库索引失效，你会怎么排查」和候选人接的
> 「我会先用 explain 看执行计划…」**被合并进了同一句**。

ASR 靠停顿断句。两人交替说话而中间停顿很短时，识别结果会把两段话并成一句。
这意味着 **s4 问答切分不能假设“一句 = 一个说话人的一次发言”** ——
必须能处理「同一句里混了两个角色」的情况。这一条要写进 s4 的 prompt。

### 仍然必须用真人录音验证的

1. **说话人分离的真实效果** —— 是否有说话人跳变、抢话时归错人。
   这次只有一个音色（靠语速区分），分离根本没有生效的余地。
2. 传 / 不传 `speaker_count=2` 的差异。
3. 真实录音里的环境噪声、口音、语速对准确率的影响。

## 2026-10-04 · 真实面试录音验证（关键）

素材：`2026-09-29 14-45-08杭州网营科技一面.mp3`，16.3 分钟，48kHz 立体声，23.5 MB。

**先排除了一条捷径**：检查了两个声道的相关性 —— 左右声道 RMS 完全一致、逐秒比对无差异，
说明这是**混音**而非分轨录制。所以「靠声道物理分离说话人」这条路走不通，
只能依赖 ASR 自己的分离能力。

### 链路表现：良好

| 指标 | 结果 |
|---|---|
| 输入时长 | 16.3 分钟（48kHz 立体声） |
| 转写耗时 | **约 30 秒**（提交到出结果） |
| 产出 | 125 句，识别出 2 个说话人 |
| 上传体积 | 转 16kHz 单声道后 31.3 MB |

30 秒完成 16 分钟音频，这个速度对网页应用完全够用，前端不需要长等待。

### 说话人分离：识别出了 2 人，但**标签抖动严重**

125 句被切成 **52 个回合**，其中 **40%（21 个）的回合只有 1 句话**。
真实面试的回合结构应该是「面试官问一句 → 候选人讲一大段」，长回合占多数。
单句回合占到四成，说明标签在句级别频繁跳变。

一个具体的错误片段（第 498–510 秒）：

```
[498.0] S0: 这个…相当于这个A的全部都是用Python语言去。
[504.6] S1: 做的对吧？              ← 面试官问句的后半段，被切成 S1
[506.0] S0: 对的，嗯，Python去做的…  ← 候选人的回答，被标成 S0
[510.4] S0: 嗯，你能说一下…          ← 面试官提问，又是 S0
```

一句话被从中间切开、两半分属不同说话人；紧接着候选人的回答又和面试官的提问
同属一个标签。**同一段里 S0 既在问又在答。**

**对设计的影响（重要）**：

1. **s3 角色判定不能简单地「按 speaker_id 分组投票」。** 标签本身不可靠，
   判定必须基于内容特征 —— 谁在提问、谁在展开长回答、谁说「请先自我介绍」。
2. **s4 问答切分要更多依赖内容而不是说话人标签。** 不能假设
   「一次发言 = 一个 speaker_id 的连续片段」，否则会把问答对切得支离破碎。

好在整体的粗粒度模式仍然可见（S0 多为短提问、S1 多为长回答），
所以「先粗判角色、再靠内容切分」这条路是可行的。

### 技术术语错误：严重，且集中在 AI/编程名词上

这是一场 AI 应用岗面试，出现的错误几乎全在技术名词上：

| 原词 | 识别结果 |
|---|---|
| `SQL` | `circle`（**贯穿全文，出现极频繁**） |
| `Text2SQL` | `test to circle` |
| `LangGraph` | `long graph` / `long group` |
| `RAG` | `R G` |
| `Agent` | `A` |
| `checkpointer` | `take point ter` |
| `tool node` | `to no 节点` / `to note` |
| `渐进式披露` | `鉴接数披露` / `建立式披露` |
| `精排` | `金牌` |
| `向量` | `相量` / `香量` |
| `调用模型` | `电用模型` |

`SQL → circle` 尤其麻烦：它在全文反复出现，而 circle 是个真实存在的英文单词，
模型未必会当作错误处理。

**还有一处 ASR 幻觉**：录音最后一句识别为
`啊，是说因为你没简单一点，肯够你내 관맞는 거야。` —— 中文录音里**混入了韩文**。
这是尾部噪声触发的典型 ASR 幻觉，需要在后处理时做语言过滤。

### 可用的改进手段（已查证）

`paraformer-v2` **支持自定义热词表**，录音文件识别接口通过 `vocabulary_id` 参数传入
（v1 用的是 `phrase_id`，v2 及以上不适用）。热词表结构：

```json
[{"text": "SQL", "weight": 4, "lang": "en"},
 {"text": "LangGraph", "weight": 4, "lang": "en"},
 {"text": "渐进式披露", "weight": 4, "lang": "zh"}]
```

约束：`weight` 取值 1–5（常用 4）；非 ASCII 热词总字符数 ≤ 15，纯 ASCII 按空格分段 ≤ 7；
`lang` 需与 `language_hints` 一致，否则不生效。创建时 `target_model` 必须与
实际调用的 ASR 模型一致。

**下一步值得做的**：维护一份面试常见技术名词的热词表（按岗位可分组），
在 s2 提交转写时带上。成本几乎为零，但对识别质量的改善是直接的。
